# 任务统计数据口径统一方案（最终版）

## 重新评估结论

先看全系统现状：除持续运行的养号任务外，所有任务（同屏、私信、社媒触达、内容运营、其他养号任务）的三个数字都是**子任务口径**——总计 = 该任务拆出的子任务数，执行成功 + 执行失败 ≤ 总计，差额是进行中 / 待执行。例如 15 / 11 / 4、10 / 6 / 0。

只有「Facebook 日常养号 · 持续运行」一条把执行成功写成了累计动作次数（132），和总计（20 个账号）不是一回事，才出现 660%。

所以问题不在设计，而在这条数据本身越界了。结论有两点：

1. **不新增「涉及账号」卡片**。按账号分布 tab 已经完整回答了"有哪些账号、各自成败多少"，顶部再放一个账号数会让四个卡片里混进第二种口径，正是这次出问题的根源。顶部四卡只讲一件事：子任务执行情况。
2. **不改成「总计 = 成功 + 失败」**。那样会丢掉"还有多少在跑 / 待执行"的信息，而这对运行中的任务恰恰最有价值，也会和列表页进度条对不上。

## 最终方案

### 1. 固定口径（全类型统一）

- 总计 = 该任务已拆分的子任务数（持续运行任务即"截至当前已下发的子任务数"）
- 执行成功 / 执行失败 = 已结束子任务中的成功、失败数
- 恒等约束：成功 + 失败 ≤ 总计，差额即进行中 / 待执行
- 卡片下补一行浅色说明："统计口径：子任务执行情况，成功 + 失败 + 进行中 = 总计"

### 2. 成功率改为已结束口径

成功率 = 成功 ÷ (成功 + 失败)，未结束的子任务不参与计算。现在用的是成功 ÷ 总计，运行中的任务会被低估（10 / 6 / 0 显示 60%，实际零失败）。两者都为 0 时显示「—」。

### 3. 修正越界数据

「Facebook 日常养号 · 持续运行」改为：总计 140、成功 132、失败 4（进行中 4），成功率 97%。语义是持续运行至今已下发 140 个子任务。同时检查其余任务，确保全部满足成功 + 失败 ≤ 总计。

### 4. 账号分布去重

按账号分布里同一账号重复出现（@zhang_ip、星航跨境、Lifestyle 365），是账号名单取数未去重所致；去重后各账号一行，成败重新按去重后的名单分摊，合计仍等于卡片数字。

### 5. 三个分布 tab 的合计对齐

按账号、按操作/动作、按子任务三个 tab 的成功 / 失败合计，都等于顶部卡片的成功 / 失败；按子任务 tab 额外把"进行中"的子任务显示为灰色未结束，与总计对齐。

## 涉及文件

- `src/routes/_app.tasks.list.tsx`：卡片口径说明、成功率算法、账号标签去重、子任务行未结束态
- `src/lib/operations-store.ts`：修正持续运行任务的 total，校验各 seed 的恒等约束
